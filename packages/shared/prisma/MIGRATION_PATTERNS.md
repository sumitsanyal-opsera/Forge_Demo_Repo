# Migration Patterns: Hybrid Prisma + Raw SQL Approach

## Overview

This project uses a **hybrid migration strategy** that combines Prisma's standard migration
tooling with hand-authored raw SQL for advanced PostgreSQL features (table partitioning,
partial indexes, custom triggers) that Prisma cannot express natively.

---

## Standard Prisma Migrations

Use Prisma migrations for all standard relational models:

```bash
# Create a new migration
npx prisma migrate dev --name add_pipeline_executions

# Apply migrations in production/CI
npx prisma migrate deploy

# Check migration status
npx prisma migrate status
```

Migration files live in `packages/shared/prisma/migrations/` and are committed to git.
Each migration is a directory containing a `migration.sql` file generated by Prisma.

---

## Raw SQL for Partitioned Tables

PostgreSQL declarative partitioning (`PARTITION BY RANGE`) is **not supported** by Prisma's
schema language. For time-series tables (e.g., `pipeline_execution_metrics`), we use a two-step
approach:

### Step 1 — Create an empty Prisma migration shell

```bash
npx prisma migrate dev --name add_execution_metrics_partitioned --create-only
```

This creates the migration directory without running it. It will contain a mostly empty `migration.sql`.

### Step 2 — Replace the SQL with hand-authored partitioned DDL

Edit the generated `migration.sql` to include the full partitioned table definition:

```sql
-- packages/shared/prisma/migrations/YYYYMMDDHHMMSS_add_execution_metrics_partitioned/migration.sql

CREATE TABLE pipeline_execution_metrics (
  id            UUID        NOT NULL DEFAULT gen_random_uuid(),
  pipeline_id   UUID        NOT NULL,
  org_id        UUID        NOT NULL,
  started_at    TIMESTAMPTZ NOT NULL,
  duration_ms   INTEGER,
  status        VARCHAR(50) NOT NULL,
  metadata      JSONB,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (started_at);

-- Monthly partitions — create at least 3 months ahead
CREATE TABLE pipeline_execution_metrics_2024_01
  PARTITION OF pipeline_execution_metrics
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE pipeline_execution_metrics_2024_02
  PARTITION OF pipeline_execution_metrics
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Partial indexes on the partitioned table
CREATE INDEX idx_metrics_pipeline_started
  ON pipeline_execution_metrics (pipeline_id, started_at DESC);

CREATE INDEX idx_metrics_active
  ON pipeline_execution_metrics (org_id, status)
  WHERE status IN ('in_progress', 'at_risk', 'potentially_stuck', 'confirmed_stuck');
```

### Step 3 — Apply the migration

```bash
npx prisma migrate dev
```

## Accessing Partitioned Tables via Prisma

Prisma **can query** partitioned tables normally — it just cannot create them. Add the
parent table to `schema.prisma` as you would any other model:

```prisma
model PipelineExecutionMetric {
  id         String   @id @default(uuid()) @db.Uuid
  pipelineId String   @db.Uuid @map("pipeline_id")
  orgId      String   @db.Uuid @map("org_id")
  startedAt  DateTime @map("started_at") @db.Timestamptz
  durationMs Int?     @map("duration_ms")
  status     String   @db.VarChar(50)
  metadata   Json?
  createdAt  DateTime @default(now()) @map("created_at") @db.Timestamptz

  @@map("pipeline_execution_metrics")
}
```

Mark the raw-SQL migration file with a comment header to flag it as hand-authored:

```sql
-- [HAND_AUTHORED] Partitioned table — do not regenerate with prisma migrate diff
```

## Partition Maintenance

Monthly partitions must be created in advance. A scheduled job in the detection service
creates the next two months' partitions on the 1st of each month.

```typescript
// Example: create next month's partition
await prisma.$executeRaw`
  CREATE TABLE IF NOT EXISTS pipeline_execution_metrics_${Prisma.raw(partitionName)}
    PARTITION OF pipeline_execution_metrics
    FOR VALUES FROM (${startDate}) TO (${endDate})
`;
```

> **Security note**: The partition name (`partitionName`) is a date-derived string
> computed server-side — never from user input. The date bounds (`startDate`, `endDate`)
> use Prisma parameterized values, not string interpolation.

## Concrete Example: WO-091 Full Schema Migration

Migration `20260812000000_add_all_tables` demonstrates all patterns in use simultaneously.

### Composite primary key for partitioned tables

PostgreSQL requires the partition key to be part of the primary key on declarative partitioned tables. Standard Prisma `@id` on a single UUID is incompatible:

```sql
-- Correct: composite PK including partition key
CREATE TABLE "pipeline_executions" (
    "id"          UUID        NOT NULL DEFAULT gen_random_uuid(),
    "started_at"  TIMESTAMPTZ NOT NULL,
    ...
    CONSTRAINT "pipeline_executions_pkey" PRIMARY KEY ("id", "started_at")
) PARTITION BY RANGE ("started_at");
```

In `schema.prisma`, use `@@id([id, startedAt])` instead of `@id`:

```prisma
model PipelineExecution {
  id        String   @default(uuid()) @db.Uuid
  startedAt DateTime @map("started_at") @db.Timestamptz
  ...
  @@id([id, startedAt])
  @@map("pipeline_executions")
}
```

### Composite foreign keys for partitioned table references

Any table FK-ing into a partitioned table must include the partition key:

```sql
-- execution_steps references pipeline_executions (composite PK)
FOREIGN KEY ("pipeline_execution_id", "pipeline_execution_started_at")
    REFERENCES "pipeline_executions"("id", "started_at") ON DELETE CASCADE
```

In `schema.prisma`:

```prisma
model ExecutionStep {
  pipelineExecutionId        String   @db.Uuid @map("pipeline_execution_id")
  pipelineExecutionStartedAt DateTime @map("pipeline_execution_started_at") @db.Timestamptz

  pipelineExecution PipelineExecution @relation(
    fields: [pipelineExecutionId, pipelineExecutionStartedAt],
    references: [id, startedAt],
    onDelete: Cascade
  )
  ...
}
```

### GIN indexes on JSONB columns

Always use `jsonb_path_ops` to minimize index size and support containment operators (`@>`):

```sql
CREATE INDEX "pipeline_executions_metadata_gin_idx"
    ON "pipeline_executions" USING GIN ("metadata" jsonb_path_ops);
```

### Partial unique index for NULL-key defaults

PostgreSQL treats `NULL` as distinct in unique constraints, so `@@unique([monitoredPipelineId, stepName])` does NOT prevent two org-level defaults (both `monitored_pipeline_id IS NULL`). Add a partial unique index:

```sql
-- Prevents duplicate org-level default configs
CREATE UNIQUE INDEX "threshold_configs_org_default_uidx"
    ON "threshold_configs" ("salesforce_org_id", "step_name")
    WHERE "monitored_pipeline_id" IS NULL;
```

### Audit log immutability trigger

```sql
CREATE OR REPLACE FUNCTION prevent_audit_modification()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'Audit log records are immutable: % on audit_log is not permitted', TG_OP;
END;
$$;

CREATE TRIGGER audit_immutability
    BEFORE UPDATE OR DELETE ON "audit_log"
    FOR EACH ROW
    EXECUTE FUNCTION prevent_audit_modification();
```

This is enforced at the database level — application-level guards alone are insufficient.

## Rules

1. **Never use raw string interpolation for user-provided values** — always use
   `Prisma.sql` tagged templates or the `$queryRaw`/`$executeRaw` parameterized APIs.
2. **Always test migrations** against a local Docker Compose database before committing.
3. **Label hand-authored migrations** with `-- [HAND_AUTHORED]` at the top of `migration.sql`.
4. **Commit migration files** — never regenerate them in a way that loses the raw SQL.
5. **Composite PK models** — any Prisma model for a partitioned table must use `@@id([id, startedAt])`, not `@id`. Application code must always include `startedAt` in single-row lookups.
6. **Composite FK models** — any model referencing a partitioned table must carry the partition key as an explicit field (e.g., `pipelineExecutionStartedAt`) and declare it in the `@relation` `fields`/`references` arrays.
